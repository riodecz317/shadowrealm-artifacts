The Agent Relay
Systems Architecture · Adapted from the GitHub-fetch relay design

The Agent Relay

The same caching/queueing/edge pattern used for a GitHub-data dashboard, re-derived for a fleet of Claude-powered financial agents — behavioral-spending-analyst, financial-performance-rating, money-risk-management, buffett-style-alignment, and data-privacy-auditor — served to iOS, Android, and Web at once. Every timing and token figure below is measured from this project's own pilot runs, not assumed.

00

Why this isn't a straight port

The reference design optimizes for a fast, deterministic, rate-limited REST API (GitHub). An LLM agent call is none of those three things. Four properties change the architecture, not just the labels on the boxes.

GitHub-fetch design assumed

Sub-2-second responses. A GitHub API call for the same repo returns the same bytes every time. Rate limits are GitHub's, fixed and published. Many users share one repo → one fetch serves all of them.

What this system actually has

35 seconds to 4.6 minutes per agent call, measured. The same agent given the same input can score it differently run to run — proven in this project's own eval pilot. Rate limits are the model provider's, usage-tier-dependent. Every user's financial data is unique — nothing to batch across users.

The four adaptations that actually matter

1. Latency, not milliseconds. An agent call is 15–100× slower than a GitHub fetch. Stale-while-revalidate stops being a nice-to-have and becomes the only way the UI ever feels responsive.

2. Non-determinism is a first-class risk, not an edge case. This project's own regression pilot found two identical financial fixtures — same numbers, only a name and city swapped — score 45 vs. 38 from the same agent. A relay that caches an agent's answer as "the" answer, forever, freezes in whichever run happened to land. The cache needs an expiry tied to agent-version hash, and a background consistency check, not just a TTL.

3. "Batching" doesn't mean the same thing. GitHub-fetch batching merges different users' requests for the same resource. There's no equivalent here — one person's financial analysis can't be merged with another's. What replaces it is fan-out/fan-in: one report (a "Ledger Read") is 4–5 independent agent calls that must run in parallel and then be assembled, not one call that serves many people.

4. A wrong answer is a different kind of failure than a slow one. GitHub rate-limiting degrades speed. An agent giving a subtly wrong risk assessment degrades trust. That's why an evaluator step belongs in the architecture itself, not just in a test suite off to the side.

The user never waits on the slowest agent synchronously — they see the old report immediately, then get pushed the new one whenever the fan-out finishes. This is the same stale-while-revalidate idea as the reference design, just load-bearing here because the wait is minutes, not seconds.

03

Cache Service — versioned by content hash, not just time

This is the layer that changes the most. A GitHub API response is cacheable because it's deterministic. An agent's output is cacheable only until either the input or the agent itself changes — so the cache key has to encode both.

Cache key = agent name + agent-version-hash + input-hash Redis

Directly reuses this project's own ai-eval/results/baseline.md model: every agent definition is content-hashed (sha256sum | cut -c1-12). When an agent's prompt is edited, its hash changes, and every cache entry keyed to the old hash is unreachable — no manual invalidation step, no stale-forever entries. In production this is the same mechanism the project's PostToolUse hook already uses in development, just applied to the live cache instead of a local markdown file.

TTL is data-driven, not flat policy

The reference design used a flat 15-minute TTL because GitHub data drifts continuously. Financial data doesn't — a user's report is valid until they import a new statement or edit a wallet. Invalidate on that event, not a clock; a flat TTL either re-runs expensive agent calls for no reason or serves a report that's gone stale for a real reason (new debt logged) while the clock hasn't expired yet.

Consistency sampling, not blind trust new — no GitHub-fetch equivalent

Because two runs of the same agent on the same input can legitimately disagree (this project's BIAS-001a/b finding — a 45 vs. 38 score gap on identical numbers), a cached result is not ground truth by construction. Periodically — or whenever a user's report swings unexpectedly between refreshes — replay the input through ledger-read-evaluator exactly as the regression-sweep skill does offline. If the delta exceeds a threshold, flag the report for review before serving it as authoritative rather than silently trusting whichever run got cached first.

04

Agent Orchestration Layer

Replaces the reference design's flat worker pool. A report is a small DAG (parallel agent calls, then an optional QA gate, then aggregation), not one job per worker.

Fan-out / fan-in, not batching core difference

A "Ledger Read refresh" is 4–5 independent jobs dispatched together and joined when all complete (or after a timeout, serving whichever finished with the rest marked pending). This is exactly the pattern executed manually in this project's own pilot: 10 agent invocations launched in parallel, tracked to completion, then synthesized into one report. Production needs to do that automatically — a queue that understands "these N jobs belong to one report," not just independent tasks.

Circuit breaker — against the model provider's limits was: GitHub 403

Same exponential-backoff idea as the reference (1s, 2s, 4s, 8s…), but tripped by the LLM provider's 429/529 responses instead of GitHub's rate-limit header. Usage-tier limits are typically requests-per-minute and tokens-per-minute together — a worker pool sized for request count alone can still get throttled on token volume during a burst of large-context reports.

Evaluator Worker — a QA gate in the critical path, not a side test suite

Route a finding through ledger-read-evaluator before it's cached whenever it falls in a flagged category (this project's own test-bank categories: Safety, Adversarial/injection, Privacy). This costs a second model call (observed: 35–150s, 8K–31K tokens per grading pass) but catches exactly the failure this pilot demonstrated in ADV-001 — a transaction note engineered to look like a system instruction — before it ever reaches a user, not after.

Tech stack

An honest scoping note

This project's agent definitions today (.claude/agents/*.md) are Claude Code subagent instructions — they run inside a Claude Code session, a single-user developer tool, not a multi-tenant backend. Everything in that instruction text (the guardrails, the evidence-tier scales, the reasoning-chain structure) is portable prompt engineering and carries over directly. What doesn't carry over as-is is the runtime: an always-on relay serving thousands of users needs the Agent Workers calling the Claude API (or Managed Agents) directly from custom backend code, not shelling out to a Claude Code CLI session. Treat this repo's agent files as the source of truth for prompts to port, not as the production worker code itself.

Monitoring & alerting

The reference design's alerts (queue length, API latency, rate-limit remaining) all carry over. Two are new, both direct products of this project's own eval work.

Consistency-drift alert new

Page when a live consistency sample (§03) finds a score delta past threshold on identical input — this is the production version of the ledger-read-evaluator's Consistency dimension, running continuously instead of only in the offline test bank.

Severity-tier alert new

Page immediately on any 🔴 Critical evaluator finding in production (a fabricated fact, a dangerous recommendation, compliance with an injected instruction) — reuse this project's own severity scale (🔴 Critical / 🟠 Major / 🟡 Minor / 🟢 Pass) as the literal alerting taxonomy rather than inventing a separate one.

Cost — measured tokens, current pricing

claude-sonnet-5 list pricing: $2.00 / MTok input, $10.00 / MTok output. This project's pilot didn't log the input/output split, so the range below is bounded honestly rather than presented as one precise number.

ItemTokens (observed)Cost range (bounded, not exact)

+ evaluator QA gate on flagged findings+8K – 31K per finding+$0.02 – $0.31 per finding
Infra (K8s nodes, RDS, Redis, MQ, LB, CDN) — reference design's estimate, largely unaffected by the agent-vs-GitHub swap—~$605 / month

At 2,000 users refreshing once a week: ~8,000 reports/month × $0.42–$2.60 ≈ $3,400 – $20,800/month in model spend — the dominant cost, unlike the GitHub-fetch design where infra dominated at ~$605/month against near-zero marginal API cost. Batch API (50% cost, for non-latency-sensitive nightly report refreshes rather than on-demand ones) and prompt caching (stable system-prompt content across a user's repeated refreshes) are the first two levers worth measuring before anything else.

Key takeaways

Scalability

Scale by parallel fan-out per report, not by request throughput alone — the bottleneck is concurrent agent-worker slots (each held for minutes), not request count.

Network

There's nothing to batch across users the way GitHub-fetch batches shared repos. The network win here is caching + stale-while-revalidate, not request coalescing.

Efficiency

The expensive resource is model tokens, not bandwidth. Cache-hit rate and evaluator-gate scoping (only flagged categories) are the two levers that actually move the cost curve.

Trust

Not in the original brief, but load-bearing here: an agent can be confidently wrong. The evaluator + consistency-sampling loop exists because "fast and cached" isn't the same guarantee as "correct."
